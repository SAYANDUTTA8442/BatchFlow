# BatchFlow — Database Schema Design

**Document:** docs/database-schema.md  
**Product:** BatchFlow  
**Status:** Proposed logical and relational schema  
**Version:** 1.0  
**Last updated:** 2026-11-17  
**Related documents:** [Requirements.md](../Requirements.md) · [architecture.md](./architecture.md)

> This is a design specification, not an implemented PostgreSQL schema. No migrations or application models are implied to exist yet. Types and constraints below are proposed PostgreSQL definitions and must be validated in migrations and integration tests.

---

## 1. Design objectives

The database must support the BatchFlow MVP while preserving transaction integrity and traceability.

1. Keep one authoritative record for each posted business transaction.
2. Make the stock-movement ledger authoritative for physical inventory.
3. Keep physical stock balances and reservations distinct.
4. Preserve the master-data, BOM and pricing context used by posted transactions.
5. Represent quantities and money with exact numeric types.
6. Support atomic production, purchase receipt, invoice, dispatch and payment operations.
7. Enforce referential integrity and prevent duplicate business effects.
8. Support the benchmark without hardcoding benchmark values into the schema.

PostgreSQL is the single authoritative database. Logical modules are represented by table boundaries in one database; separate PostgreSQL schemas are unnecessary for the MVP.

## 2. Conventions and data types

### 2.1 Naming and identifiers

- Tables and columns use lowercase snake_case.
- Primary keys use id; foreign keys use the referenced entity name plus _id.
- Ordinary relational records use BIGINT GENERATED BY DEFAULT AS IDENTITY.
- UUIDs are used for externally supplied request/correlation identifiers where appropriate.
- Timestamps use TIMESTAMPTZ and are stored in UTC. Business dates use DATE.
- Status values use VARCHAR plus CHECK constraints initially, so status evolution remains manageable.
- Master records that must remain historically referencable are deactivated, not hard-deleted.

### 2.2 Numeric precision

| Purpose | Proposed PostgreSQL type | Rule |
|---|---|---|
| Inventory quantity | NUMERIC(18,6) | Exact quantity |
| Unit conversion factor | NUMERIC(18,9) | Exact configured conversion |
| Unit rate / valuation rate | NUMERIC(18,6) | Retains rates such as ₹43.125/kg |
| Monetary line/header amount | NUMERIC(18,2) | INR precision for MVP |
| GST rate / percentage | NUMERIC(9,4) | Exact rate |
| Variance percentage | NUMERIC(12,4) | Calculated percentage |

Python calculations use Decimal, never float, for money or stock quantities. API responses serialize decimals as strings or another documented exact representation.

Quantities on source document lines are non-negative. Stock movements use signed quantities: positive for receipts/output and negative for issues/dispatch. A movement quantity cannot be zero.

### 2.3 Common columns

Use only where appropriate:

- created_at TIMESTAMPTZ NOT NULL DEFAULT now()
- updated_at TIMESTAMPTZ NOT NULL DEFAULT now() for mutable records
- created_by_user_id BIGINT REFERENCES users(id) where actor attribution is needed
- is_active BOOLEAN NOT NULL DEFAULT true for deactivatable master records

Posted records are not edited in place. Generic soft deletion is not a substitute for transaction correction.

### 2.4 Monetary representation

Use NUMERIC, not floating-point types or PostgreSQL money. Unit rates may require more than two decimal places; extended line totals and invoice totals are rounded under an explicit policy and stored to two decimal places.

## 4. Identity and access tables

### 4.1 users

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| full_name | VARCHAR(160) | NOT NULL |
| email | CITEXT or VARCHAR(254) | NOT NULL, UNIQUE; normalize consistently |
| password_hash | TEXT | NOT NULL; never store plaintext |
| is_active | BOOLEAN | NOT NULL DEFAULT true |
| last_login_at | TIMESTAMPTZ | NULL |
| created_at / updated_at | TIMESTAMPTZ | Standard timestamps |

Do not store raw access tokens, refresh tokens or passwords here. If persisted sessions are needed, create a dedicated session table containing token hashes and expiry/revocation metadata.

### 4.2 roles and user_roles

roles: id BIGINT identity primary key; code VARCHAR(40) NOT NULL UNIQUE; name VARCHAR(100) NOT NULL; description TEXT NULL.

user_roles: user_id BIGINT FK → users.id; role_id BIGINT FK → roles.id; assigned_at TIMESTAMPTZ NOT NULL DEFAULT now(); assigned_by_user_id BIGINT FK → users.id NULL. Composite primary key: (user_id, role_id).

Seed role codes: salesman, admin, production, auditor, owner. Multiple roles per user are supported.

### 4.3 permissions and role_permissions (optional)

If permission records are stored in the database, use permissions(id, code UNIQUE, description) and role_permissions(role_id, permission_id, PRIMARY KEY(role_id, permission_id)). For the first implementation, role checks may remain in application policy code. Do not build a complex dynamic policy engine for the MVP. Record-level rules still require application-service checks.

## 5. Master data tables

### 5.1 units

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| code | VARCHAR(20) | NOT NULL UNIQUE; KG, G, L, PCS, PACKET |
| name | VARCHAR(80) | NOT NULL |
| dimension | VARCHAR(20) | NOT NULL; MASS, VOLUME, COUNT |
| is_base_unit | BOOLEAN | NOT NULL DEFAULT false |
| is_active | BOOLEAN | NOT NULL DEFAULT true |

Seed the units required by the benchmark. Choose one canonical inventory unit for each item. Generic conversion must never cross dimensions.

### 5.2 unit_conversions

id BIGINT identity primary key; from_unit_id BIGINT FK → units.id NOT NULL; to_unit_id BIGINT FK → units.id NOT NULL; factor NUMERIC(18,9) NOT NULL CHECK (factor > 0).

Unique: (from_unit_id, to_unit_id). Validate equal dimensions in the service or a trigger; a row CHECK cannot inspect referenced units. Example: 1 kg = 1,000 g. Carton capacity is not a generic conversion; it is product-specific packaging configuration.

### 5.3 inventory_items

One inventory identity for every stocked item: raw material, packaging material or finished good.

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| code | VARCHAR(60) | NOT NULL UNIQUE |
| name | VARCHAR(160) | NOT NULL |
| category | VARCHAR(30) | CHECK IN (RAW_MATERIAL, PACKAGING, FINISHED_GOOD) |
| base_unit_id | BIGINT | FK → units.id, NOT NULL |
| is_active | BOOLEAN | NOT NULL DEFAULT true |
| created_at / updated_at | TIMESTAMPTZ | Standard timestamps |

All stock quantities use the item's base unit. Material-specific conversion may be configured where necessary; do not infer density-based mass/volume conversion.

### 5.4 products

Each sales product maps to exactly one finished-good inventory item.

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| inventory_item_id | BIGINT | FK → inventory_items.id, NOT NULL UNIQUE |
| sku | VARCHAR(60) | NOT NULL UNIQUE |
| name | VARCHAR(160) | NOT NULL |
| pack_size_value | NUMERIC(18,6) | NULL; e.g. 200 |
| pack_size_unit_id | BIGINT | FK → units.id, NULL |
| hsn_code | VARCHAR(20) | NULL |
| default_selling_price | NUMERIC(18,6) | NOT NULL CHECK (>= 0) |
| is_active | BOOLEAN | NOT NULL DEFAULT true |
| created_at / updated_at | TIMESTAMPTZ | Standard timestamps |

The referenced inventory item must have category FINISHED_GOOD. Enforce this in the service and optionally a trigger. Snapshot SKU, description, HSN, unit and price into transaction lines.

### 5.5 customers

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| customer_code | VARCHAR(60) | NOT NULL UNIQUE |
| name | VARCHAR(180) | NOT NULL |
| customer_type | VARCHAR(20) | CHECK IN (RETAILER, DISTRIBUTOR) |
| billing_address / shipping_address | TEXT | NULL |
| state_code | VARCHAR(2) | NOT NULL; configured Indian state/UT code |
| gstin | VARCHAR(15) | NULL |
| is_active | BOOLEAN | NOT NULL DEFAULT true |
| created_at / updated_at | TIMESTAMPTZ | Standard timestamps |

GSTIN format/state validation belongs in a dedicated validator. Do not require a GSTIN for every customer unless the business rule requires it.

### 5.6 customer_salesmen

customer_id BIGINT FK → customers.id; salesman_user_id BIGINT FK → users.id; assigned_at TIMESTAMPTZ NOT NULL DEFAULT now(); assigned_by_user_id BIGINT FK → users.id NULL.

Composite primary key: (customer_id, salesman_user_id). Authorization must verify assignment when submitting and retrieving orders.

### 5.7 suppliers

id BIGINT identity primary key; supplier_code VARCHAR(60) NOT NULL UNIQUE; name VARCHAR(180) NOT NULL; address TEXT NULL; state_code VARCHAR(2) NULL; gstin VARCHAR(15) NULL; phone VARCHAR(30) NULL; is_active BOOLEAN NOT NULL DEFAULT true; created_at / updated_at TIMESTAMPTZ.

### 5.8 inventory_locations

id BIGINT identity primary key; code VARCHAR(40) NOT NULL UNIQUE; name VARCHAR(120) NOT NULL; is_active BOOLEAN NOT NULL DEFAULT true.

Seed one factory location for the MVP. Multiple factories and warehouse/bin management remain out of scope.

## 6. BOM and production tables

### 6.1 boms

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| product_id | BIGINT | FK → products.id, NOT NULL |
| version | INTEGER | NOT NULL CHECK (> 0) |
| status | VARCHAR(20) | CHECK IN (DRAFT, ACTIVE, RETIRED) |
| expected_output_qty | NUMERIC(18,6) | NOT NULL CHECK (> 0), product base unit |
| effective_from | DATE | NOT NULL |
| effective_to | DATE | NULL |
| created_by_user_id | BIGINT | FK → users.id |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

Unique: (product_id, version). Prevent overlapping active/effective BOM versions in application logic or an exclusion constraint. Once activated, a BOM version is immutable; create a new version.

### 6.2 bom_lines

id BIGINT identity primary key; bom_id BIGINT FK → boms.id NOT NULL; inventory_item_id BIGINT FK → inventory_items.id NOT NULL; line_type VARCHAR(20) CHECK IN (RAW_MATERIAL, PACKAGING); quantity_per_batch NUMERIC(18,6) NOT NULL CHECK (> 0), expressed in item base unit; notes TEXT NULL.

Unique: (bom_id, inventory_item_id). The referenced item category must match line_type. Carton capacity is product-specific packaging configuration, not a generic unit conversion.

### 6.3 production_runs

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| run_number | VARCHAR(60) | NOT NULL UNIQUE |
| product_id | BIGINT | FK → products.id, NOT NULL |
| bom_id | BIGINT | FK → boms.id, NOT NULL |
| bom_version_snapshot | INTEGER | NOT NULL |
| batch_multiplier | NUMERIC(18,6) | NOT NULL CHECK (> 0) |
| expected_output_qty | NUMERIC(18,6) | NOT NULL CHECK (> 0), snapshot |
| actual_good_output_qty | NUMERIC(18,6) | NULL until recorded; CHECK (>= 0) |
| status | VARCHAR(20) | CHECK IN (DRAFT, POSTED, REVERSED) |
| production_date | DATE | NOT NULL |
| supervisor_user_id | BIGINT | FK → users.id, NOT NULL |
| posted_at | TIMESTAMPTZ | NULL until posted |
| posted_by_user_id | BIGINT | FK → users.id, NULL |
| created_at / updated_at | TIMESTAMPTZ | Standard timestamps |

A posted run is immutable. A correction preserves the original run and creates a documented reversal/correction workflow. Define that workflow before implementing it.

### 6.4 production_run_lines

Snapshots planned and actual consumption for raw-material and packaging lines.

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| production_run_id | BIGINT | FK → production_runs.id, NOT NULL |
| inventory_item_id | BIGINT | FK → inventory_items.id, NOT NULL |
| line_type | VARCHAR(20) | CHECK IN (RAW_MATERIAL, PACKAGING) |
| item_code_snapshot | VARCHAR(60) | NOT NULL |
| item_name_snapshot | VARCHAR(160) | NOT NULL |
| base_unit_code_snapshot | VARCHAR(20) | NOT NULL |
| planned_qty | NUMERIC(18,6) | NOT NULL CHECK (>= 0) |
| actual_qty | NUMERIC(18,6) | NOT NULL CHECK (>= 0) |
| variance_qty | NUMERIC(18,6) | Snapshot: actual − planned |
| variance_percent | NUMERIC(12,4) | NULL if planned quantity is zero |
| unit_cost_snapshot | NUMERIC(18,6) | NOT NULL CHECK (>= 0) |
| line_cost | NUMERIC(18,2) | NOT NULL CHECK (>= 0) |

Unique: (production_run_id, inventory_item_id) for the MVP. Store BOM-derived planned quantities; never recompute historical plans from the current BOM after a revision. Actual packaging consumption includes damaged pouches.

### 6.5 production_run_outputs

id BIGINT identity primary key; production_run_id BIGINT FK → production_runs.id NOT NULL; product_id BIGINT FK → products.id NOT NULL; good_qty NUMERIC(18,6) NOT NULL CHECK (>= 0); base_unit_code_snapshot VARCHAR(20) NOT NULL.

Enforce one output row per run for the MVP. This makes actual good output explicit and avoids overloading the run header.

### 6.6 production_cost_lines

id BIGINT identity primary key; production_run_id BIGINT FK → production_runs.id NOT NULL; cost_type VARCHAR(30) CHECK IN (LABOUR, ENERGY, OTHER); description VARCHAR(180) NOT NULL; amount NUMERIC(18,2) NOT NULL CHECK (amount >= 0).

Material cost is derived from production_run_lines and unit-cost snapshots. Do not duplicate material cost in this table. The benchmark labour and gas/power are LABOUR and ENERGY lines.

### 7.2 purchase_receipt_lines

id BIGINT identity primary key; purchase_receipt_id BIGINT FK → purchase_receipts.id NOT NULL; inventory_item_id BIGINT FK → inventory_items.id NOT NULL; item_code_snapshot VARCHAR(60) NOT NULL; item_name_snapshot VARCHAR(160) NOT NULL; quantity_received NUMERIC(18,6) NOT NULL CHECK (> 0), base unit; unit_rate NUMERIC(18,6) NOT NULL CHECK (>= 0); line_total NUMERIC(18,2) NOT NULL CHECK (>= 0).

Posting creates positive stock movements and updates valuation/balance projections in the same transaction. Retain the receipt rate as the source rate for WAC valuation.

## 8. Sales and order tables

### 8.1 sales_orders

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| order_number | VARCHAR(60) | NOT NULL UNIQUE |
| customer_id | BIGINT | FK → customers.id, NOT NULL |
| salesman_user_id | BIGINT | FK → users.id, NOT NULL |
| status | VARCHAR(24) | CHECK IN (SUBMITTED, APPROVED, REJECTED, INVOICED, DISPATCHED) |
| submitted_at | TIMESTAMPTZ | NOT NULL |
| reviewed_at | TIMESTAMPTZ | NULL |
| reviewed_by_user_id | BIGINT | FK → users.id, NULL |
| review_note | TEXT | NULL |
| created_at / updated_at | TIMESTAMPTZ | Standard timestamps |

Order status is not physical inventory status. Do not mark an order dispatched until its required quantity is fulfilled under the supported dispatch policy.

### 8.2 sales_order_lines

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| sales_order_id | BIGINT | FK → sales_orders.id, NOT NULL |
| product_id | BIGINT | FK → products.id, NOT NULL |
| sku_snapshot | VARCHAR(60) | NOT NULL |
| product_name_snapshot | VARCHAR(160) | NOT NULL |
| hsn_snapshot | VARCHAR(20) | NULL |
| quantity | NUMERIC(18,6) | NOT NULL CHECK (> 0), product base unit |
| unit_price | NUMERIC(18,6) | NOT NULL CHECK (>= 0) |
| line_taxable_value | NUMERIC(18,2) | Calculated snapshot |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

Order lines preserve submitted/reviewed prices and product descriptions. If admin review changes quantity or price, record an audit event and retain final approved values. Decide whether a separate order-revision table is needed after designing the review workflow.

### 8.3 order_reservations

Represents stock committed to an approved order without reducing physical on-hand stock.

id BIGINT identity primary key; sales_order_id BIGINT FK → sales_orders.id NOT NULL; sales_order_line_id BIGINT FK → sales_order_lines.id NOT NULL; inventory_item_id BIGINT FK → inventory_items.id NOT NULL; quantity_reserved NUMERIC(18,6) NOT NULL CHECK (> 0); quantity_consumed NUMERIC(18,6) NOT NULL DEFAULT 0 CHECK (>= 0); status VARCHAR(20) CHECK IN (ACTIVE, CONSUMED, RELEASED); created_at TIMESTAMPTZ NOT NULL DEFAULT now(); released_at TIMESTAMPTZ NULL.

Consumed quantity cannot exceed reserved quantity. Active reservations reduce available-to-promise, not on-hand. Exact partial-dispatch and release rules remain open decisions.

## 9. Billing and invoice tables

### 9.1 invoice_series

Serializes invoice-number allocation by financial year and series.

id BIGINT identity primary key; series_code VARCHAR(30) NOT NULL; financial_year VARCHAR(9) NOT NULL; prefix VARCHAR(30) NOT NULL; next_number BIGINT NOT NULL CHECK (> 0).

Unique: (series_code, financial_year). Allocate a number by locking the relevant row and incrementing it inside the invoice-issuance transaction. Never use an unprotected MAX(number)+1 query.

### 9.2 invoices

One invoice per approved sales order in the initial MVP.

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| sales_order_id | BIGINT | FK → sales_orders.id, NOT NULL UNIQUE |
| invoice_series_id | BIGINT | FK → invoice_series.id, NOT NULL |
| invoice_number | VARCHAR(60) | NOT NULL UNIQUE |
| invoice_date | DATE | NOT NULL |
| seller_name_snapshot | VARCHAR(180) | NOT NULL |
| seller_gstin_snapshot | VARCHAR(15) | NULL |
| seller_state_code_snapshot | VARCHAR(2) | NOT NULL |
| customer_name_snapshot | VARCHAR(180) | NOT NULL |
| customer_gstin_snapshot | VARCHAR(15) | NULL |
| customer_address_snapshot | TEXT | NULL |
| customer_state_code_snapshot | VARCHAR(2) | NOT NULL |
| tax_treatment | VARCHAR(10) | CHECK IN (INTRA_STATE, INTER_STATE) |
| taxable_total | NUMERIC(18,2) | NOT NULL CHECK (>= 0) |
| cgst_total / sgst_total / igst_total | NUMERIC(18,2) | NOT NULL DEFAULT 0 CHECK (>= 0) |
| grand_total | NUMERIC(18,2) | NOT NULL CHECK (>= 0) |
| status | VARCHAR(20) | Initial value ISSUED; correction policy to be finalized |
| issued_at | TIMESTAMPTZ | NOT NULL |
| issued_by_user_id | BIGINT | FK → users.id, NOT NULL |

The invoice is a historical snapshot. Master-data edits must not rewrite it. Issued invoices cannot be deleted. Cancellation/credit-note representation requires a separately approved correction policy.

### 9.3 invoice_lines

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| invoice_id | BIGINT | FK → invoices.id, NOT NULL |
| product_id | BIGINT | FK → products.id, NOT NULL |
| sku_snapshot | VARCHAR(60) | NOT NULL |
| description_snapshot | VARCHAR(180) | NOT NULL |
| hsn_snapshot | VARCHAR(20) | NULL |
| quantity | NUMERIC(18,6) | NOT NULL CHECK (> 0) |
| unit_price | NUMERIC(18,6) | NOT NULL CHECK (>= 0) |
| taxable_value | NUMERIC(18,2) | NOT NULL CHECK (>= 0) |
| gst_rate | NUMERIC(9,4) | NOT NULL CHECK (>= 0) |
| cgst_amount / sgst_amount / igst_amount | NUMERIC(18,2) | NOT NULL DEFAULT 0 CHECK (>= 0) |
| line_total | NUMERIC(18,2) | NOT NULL CHECK (>= 0) |

Line totals must reconcile with invoice header totals. Enforce this in the issuance service and integration tests; a row CHECK cannot aggregate child rows. Retailer A's benchmark invoice must total ₹7,875, with taxable value ₹7,500, CGST ₹187.50 and SGST ₹187.50.

## 10. Dispatch tables

### 10.1 dispatches

id BIGINT identity primary key; dispatch_number VARCHAR(60) NOT NULL UNIQUE; invoice_id BIGINT FK → invoices.id NOT NULL; dispatched_at TIMESTAMPTZ NOT NULL; dispatched_by_user_id BIGINT FK → users.id NOT NULL; status VARCHAR(20) CHECK IN (POSTED, REVERSED); created_at TIMESTAMPTZ NOT NULL DEFAULT now().

For the first MVP, use one full dispatch per invoice unless partial dispatch is explicitly approved. If full-only, add UNIQUE(invoice_id). If partial dispatch is supported, enforce cumulative dispatched quantity against invoice lines.

### 10.2 dispatch_lines

id BIGINT identity primary key; dispatch_id BIGINT FK → dispatches.id NOT NULL; invoice_line_id BIGINT FK → invoice_lines.id NOT NULL; inventory_item_id BIGINT FK → inventory_items.id NOT NULL; quantity_dispatched NUMERIC(18,6) NOT NULL CHECK (> 0).

A posted dispatch line creates a negative finished-goods movement. The invoice line and dispatch line must identify the same product inventory item; enforce this in the service or with composite foreign keys.

## 11. Receivables and payment tables

### 11.1 payments

id BIGINT identity primary key; payment_reference VARCHAR(80) NULL; customer_id BIGINT FK → customers.id NOT NULL; payment_date DATE NOT NULL; amount NUMERIC(18,2) NOT NULL CHECK (> 0); method VARCHAR(30) NULL; note TEXT NULL; recorded_by_user_id BIGINT FK → users.id NOT NULL; created_at TIMESTAMPTZ NOT NULL DEFAULT now().

### 11.2 payment_allocations

id BIGINT identity primary key; payment_id BIGINT FK → payments.id NOT NULL; invoice_id BIGINT FK → invoices.id NOT NULL; allocated_amount NUMERIC(18,2) NOT NULL CHECK (> 0); created_at TIMESTAMPTZ NOT NULL DEFAULT now().

A payment may be allocated across invoices; an invoice may receive multiple payments. Allocations cannot exceed payment amount under the initial policy. Validate that payment customer matches invoice customer in the application service.

Outstanding is derived as invoice grand total minus valid allocations, subject to future credit-note/cancellation rules. Do not store an independently editable outstanding amount. Benchmark: ₹7,875 − ₹4,000 = ₹3,875.

## 12. Inventory ledger and valuation tables

### 12.1 stock_movements

This is the authoritative physical stock ledger. Rows are append-only after posting.

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| inventory_item_id | BIGINT | FK → inventory_items.id, NOT NULL |
| inventory_location_id | BIGINT | FK → inventory_locations.id, NOT NULL |
| movement_type | VARCHAR(30) | OPENING, PURCHASE_RECEIPT, PRODUCTION_ISSUE, PRODUCTION_OUTPUT, DISPATCH, ADJUSTMENT, REVERSAL |
| quantity_delta | NUMERIC(18,6) | NOT NULL CHECK (<> 0); signed quantity |
| unit_cost | NUMERIC(18,6) | NULL where not applicable; otherwise >= 0 |
| extended_cost | NUMERIC(18,2) | NULL where not applicable; otherwise >= 0 |
| purchase_receipt_line_id | BIGINT | FK → purchase_receipt_lines.id, NULL |
| production_run_line_id | BIGINT | FK → production_run_lines.id, NULL |
| production_run_output_id | BIGINT | FK → production_run_outputs.id, NULL |
| dispatch_line_id | BIGINT | FK → dispatch_lines.id, NULL |
| stock_adjustment_line_id | BIGINT | FK → stock_adjustment_lines.id, NULL |
| reverses_movement_id | BIGINT | Self-FK → stock_movements.id, NULL |
| posted_at | TIMESTAMPTZ | NOT NULL |
| posted_by_user_id | BIGINT | FK → users.id, NULL for controlled seed/system posting |

Exactly one source-line FK must be populated for each movement. Enforce with a CHECK constraint. Add uniqueness on the appropriate source-line/movement combination to prevent duplicate posting. A reversal references the original movement and uses the opposite quantity sign; validate reversal correctness in the posting service and tests.

Explicit source-line foreign keys are preferred to a free-form source_type + source_id pair because ordinary foreign keys can protect source-line existence. The source header is reached through the source line.

Do not update or delete posted movements. Correct errors with a new reversal/adjustment movement that preserves original history.

### 12.2 inventory_balances

A transactionally maintained projection for fast stock reads.

| Column | Type | Constraints / notes |
|---|---|---|
| inventory_item_id | BIGINT | FK → inventory_items.id |
| inventory_location_id | BIGINT | FK → inventory_locations.id |
| on_hand_qty | NUMERIC(18,6) | NOT NULL DEFAULT 0 CHECK (>= 0) |
| updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

Composite primary key: (inventory_item_id, inventory_location_id). Update in the same transaction as its stock movement. Reconciliation compares on_hand_qty with SUM(stock_movements.quantity_delta) for the same item/location. Never update this projection without writing a corresponding ledger movement.

### 12.3 inventory_valuations

Current moving weighted-average valuation projection per item/location.

| Column | Type | Constraints / notes |
|---|---|---|
| inventory_item_id | BIGINT | FK → inventory_items.id |
| inventory_location_id | BIGINT | FK → inventory_locations.id |
| valued_qty | NUMERIC(18,6) | NOT NULL DEFAULT 0 CHECK (>= 0) |
| inventory_value | NUMERIC(18,2) | NOT NULL DEFAULT 0 CHECK (>= 0) |
| average_unit_cost | NUMERIC(18,6) | NOT NULL DEFAULT 0 CHECK (>= 0) |
| updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

Composite primary key: (inventory_item_id, inventory_location_id). This is a valuation projection, not a replacement for movement cost snapshots. Receipt and issue posting update it transactionally under the same item/location lock. Define WAC rounding and negative-stock policy in the transaction design. Negative stock is prohibited in the MVP.

### 12.4 stock_adjustments and stock_adjustment_lines

Use an explicit adjustment document for opening balances and later controlled corrections.

stock_adjustments:
- id BIGINT identity primary key
- adjustment_number VARCHAR(60) NOT NULL UNIQUE
- reason VARCHAR(30) NOT NULL CHECK IN (OPENING_BALANCE, COUNT_CORRECTION, OTHER)
- note TEXT NULL
- status VARCHAR(20) NOT NULL CHECK IN (DRAFT, POSTED)
- created_by_user_id BIGINT FK → users.id NOT NULL
- posted_by_user_id BIGINT FK → users.id NULL
- posted_at TIMESTAMPTZ NULL
- created_at TIMESTAMPTZ NOT NULL DEFAULT now()

stock_adjustment_lines:
- id BIGINT identity primary key
- stock_adjustment_id BIGINT FK → stock_adjustments.id NOT NULL
- inventory_item_id BIGINT FK → inventory_items.id NOT NULL
- inventory_location_id BIGINT FK → inventory_locations.id NOT NULL
- quantity_delta NUMERIC(18,6) NOT NULL CHECK (<> 0)
- unit_cost NUMERIC(18,6) NULL CHECK (>= 0)
- note TEXT NULL

Posting creates stock movements linked to each adjustment line. Opening balances and initial valuation rates must use this controlled path, not direct balance updates.

## 13. Audit and idempotency tables

### 13.1 audit_events

Append-only record of significant business actions.

| Column | Type | Constraints / notes |
|---|---|---|
| id | BIGINT identity | Primary key |
| actor_user_id | BIGINT | FK → users.id, NULL for controlled system action |
| action | VARCHAR(80) | NOT NULL |
| entity_type | VARCHAR(60) | NOT NULL |
| entity_id | BIGINT | NOT NULL; generic reference, not a relational FK |
| occurred_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |
| request_id | UUID | NULL; correlation identifier |
| before_data | JSONB | NULL; omit secrets |
| after_data | JSONB | NULL; omit secrets |
| metadata | JSONB | NULL; structured context |

The generic entity reference is acceptable here because audit events intentionally span multiple entity types. It is not a business referential-integrity mechanism. Ordinary application roles must not edit or delete audit rows.

### 13.2 idempotency_records

Protects retried post requests from repeating business effects.

id BIGINT identity primary key; scope VARCHAR(80) NOT NULL; idempotency_key VARCHAR(160) NOT NULL; request_hash VARCHAR(128) NOT NULL; response_status INTEGER NULL until completed; response_body JSONB NULL until completed; created_at TIMESTAMPTZ NOT NULL DEFAULT now(); completed_at TIMESTAMPTZ NULL.

Unique: (scope, idempotency_key). Persist this record and the business effect in the same transaction. Reuse with a different request hash is rejected. Same-key/same-payload retry returns the original result.

## 14. Key constraints and indexes

### 14.1 Unique constraints

At minimum:

- users(email), roles(code)
- inventory_items(code), products(sku), products(inventory_item_id)
- customers(customer_code), suppliers(supplier_code)
- boms(product_id, version)
- sales_orders(order_number), purchase_receipts(receipt_number), production_runs(run_number)
- invoices(sales_order_id) for one invoice per order in MVP
- invoices(invoice_number), invoice_series(series_code, financial_year)
- dispatches(dispatch_number)
- idempotency_records(scope, idempotency_key)
- Composite primary keys described for link and balance tables.

### 14.2 Check constraints

- Non-negative quantities/rates/amounts where applicable.
- Non-zero posted stock movement quantity.
- Exactly one stock movement source-line FK populated.
- Non-negative planned and actual production quantities.
- Reservation consumed quantity does not exceed reserved quantity.
- Non-negative invoice tax and totals.
- Positive payment allocations.
- Non-negative inventory on-hand and valuation quantities.
- Positive unit conversion factors.
- Status values constrained to documented states.

Cross-row invariants—invoice header totals matching lines, payment allocations not exceeding payment amount, and dispatch product matching invoice product—must be enforced in transaction services and integration tests. Use triggers only where a database-level guarantee is valuable and maintainable.

### 14.3 Indexes

Recommended indexes:

- Foreign-key columns used in joins and delete/restriction checks.
- sales_orders(status, submitted_at)
- sales_orders(salesman_user_id, submitted_at)
- sales_orders(customer_id, submitted_at)
- purchase_receipts(receipt_date, status)
- production_runs(production_date, status)
- invoices(invoice_date, customer_state_code_snapshot)
- payment_allocations(invoice_id)
- payments(customer_id, payment_date)
- stock_movements(inventory_item_id, inventory_location_id, posted_at)
- Each stock movement source FK
- audit_events(entity_type, entity_id, occurred_at)
- audit_events(actor_user_id, occurred_at)

Do not index every column. Validate query plans against actual availability and report queries.

## 15. Important invariants

### 15.1 Inventory

1. Every posted physical stock change has exactly one source line.
2. A source line cannot be posted twice.
3. The balance projection equals the sum of posted movement deltas for each item/location.
4. Reservations do not change on-hand stock.
5. Dispatch and production posting cannot create negative on-hand stock.
6. Reversal is a new movement; original history remains.
7. Stock-sensitive transactions lock and recheck the relevant balance before posting.

### 15.2 Production

1. A posted run has a BOM version and snapshot of the BOM-derived plan.
2. Actual raw-material and packaging quantities are separate from planned quantities.
3. Damaged pouches count as packaging consumption, not good output.
4. Finished-goods output equals actual good output.
5. Material issues, packaging issues, output receipts, variances, cost data and audit event commit atomically.
6. Later BOM edits do not change historical production calculations.

### 15.3 Sales and billing

1. A salesman submits orders only for assigned customers.
2. An order must be approved before invoice issuance.
3. An issued invoice is an immutable snapshot.
4. Invoice-number allocation is serialized and unique within its series.
5. Invoice issuance does not reduce physical stock.
6. Dispatch references an eligible invoice and creates the stock issue atomically.
7. Duplicate dispatch requests cannot create duplicate movements.

### 15.4 Payments

1. A payment has a positive amount.
2. Allocations reference existing invoices.
3. Allocated total cannot exceed payment amount under the initial policy.
4. Outstanding is derived from invoice totals and valid allocations, not manually edited.

## 17. Deliberate exclusions

Do not add these without a concrete requirement:

- Multi-tenant organization tables.
- Multi-factory and warehouse-bin hierarchy.
- Batch/lot/expiry/FEFO tables.
- Work-in-progress inventory.
- Full purchase-order approval workflow.
- Full general ledger and journal accounting.
- GST portal filing/statutory return tables.
- Payment gateway/bank reconciliation.
- Event broker/outbox infrastructure.
- Analytics warehouse or separate reporting database.

These may be future extensions. Keep the initial schema small enough to understand and test.

## 18. Open decisions before migrations

Resolve these before the relevant migration or workflow is finalized:

1. Authentication sessions: cookie session versus bearer token, and whether a persisted session table is required.
2. Reservation lifecycle: release behavior on rejected/cancelled orders and whether reservations are mandatory in MVP.
3. Partial dispatch: full dispatch only or multiple dispatches per invoice.
4. Invoice correction: cancellation/credit-note data model and numbering rules.
5. Payment edge cases: overpayments, unallocated receipts and allocation changes.
6. Inventory location policy: one seeded factory location versus location selection in UI.
7. Unit precision: allowed precision and rounding for each stocked item.
8. WAC policy: exact receipt/issue update and rounding policy, including reversals.
9. Production correction: reversal and re-posting model for a posted run.
10. Order review history: whether a dedicated order-revision table is required beyond audit events.

Do not silently choose behavior for these cases in endpoint code. Record decisions in docs/transaction-design.md or a short architecture decision record before implementation.

## 19. Proposed migration order

Build the schema in dependency order. Keep migrations small and reviewable.

1. Extensions and shared lookup/reference tables (units, roles, permissions).
2. Users and role assignments.
3. Inventory locations and inventory items.
4. Products, customers, customer-salesman assignments and suppliers.
5. Unit conversions.
6. BOM headers and lines.
7. Purchase receipts and lines.
8. Sales orders and lines.
9. Production runs, consumption lines, outputs and cost lines.
10. Reservations.
11. Invoice series, invoices and invoice lines.
12. Dispatches and dispatch lines.
13. Stock adjustments, stock movements, inventory balances and valuations.
14. Payments and allocations.
15. Audit events and idempotency records.
16. Indexes, partial unique constraints and any carefully justified triggers.

Exact migration grouping may change to resolve circular foreign keys. Do not create all tables in one unreviewable migration.
